# 多池与 ParaSwap：同轮四方比较和差距诊断

## 结论

本轮实际比较了原有单路径、两池、多池和 ParaSwap，而不再只用“相对自己单路径的提升”
推测外部差距。四方均成功返回 90/90 组报价。相对 ParaSwap 的输出差距在 ±0.5% 内的样本：
**单路径 85/90、两池 87/90、多池 88/90**。

SHIB 六组多池输出全部高于两池，且都进入 ±0.5%。大额买入的差距约从 −1.8821%（单路径）、
−0.8294%（两池）缩至 **−0.1697%（多池）**。但仍不能宣称完全追平：白名单外路径、未支持
的平台、网格精度和多跳分支仍有影响；DAI→WETH 还有两项较大负向离群点。

本轮也完成了实际 HTTP/Viewer 接入：`split=true` 触发固定区块的多池询价，响应明确表示
并行分支。旧请求保持单路径格式。实现与接口说明见 [MULTI-POOL](../MULTI-POOL.md)。

原始依据：[完整报告](2026-11-02-multi-pool-vs-paraswap.md)、
[原始 JSON、路径及回放](2026-11-02-multi-pool-vs-paraswap.json)。

## 实验方法

- 原有 30 个方向 × 3 档固定 raw 输入，合计 90 组，未删去无收益或表现较差的样本。
- 每行先请求 ParaSwap，再选择其可用的报告区块，否则使用当前 head；单路径、两池、多池
  在同一固定区块、同一图/报价源/快照中比较。两池和多池的调用顺序逐行交替。
- 本地定价区块范围 **26325701–26325776**，所有记录的区块哈希在结束时校验；共享区块的
  每行哈希也检查一致。源代码指纹、git/dirty 状态、实际配置、池清单与语料都保存在 JSON。
- ParaSwap 实时报价可能含有不同区块的缓存池状态；其原始报告输出和统一区块重估的分配
  是两种不同参照，不混作同区块精确成交证明。
- 多池最多四个候选池/四个分支，20 段分配网格，256 次额外适配器调用，搜索并发 8、预算 8 秒。
  两池使用相同配置但分支上限为 2。图仍为 209 个 AMM 池 + 1 个 wrapper link、48 个代币、432 条边。
- debug 构建、公共 RPC，每行重新构建固定区块定价上下文。计时区分上下文准备、两池、
  多池和诊断回放；不把整个实验行耗时当成一次用户询价延迟。
- 毛输出比较不含额外 gas、MEV、实际成交或交易构建。

## 全量报价质量

差距公式：`(本地输出 − ParaSwap 输出) / ParaSwap 输出`。

| 指标 | 单路径 | 两池 | 多池 |
|---|---:|---:|---:|
| 与 ParaSwap 可比较样本 | 90 | 90 | 90 |
| 输出差距中位数 | −0.001389% | −0.000960% | −0.000960% |
| 输出差距等权均值 | −0.095714% | −0.050302% | **−0.037133%** |
| 差距在 ±0.5% 内 | 85/90 | 87/90 | **88/90（97.8%）** |

多池相对单路径：35 组输出增加、55 组保留原路径。相对两池：**13 组严格增加、77 组相同、
0 组减少**；严格增加也包括很小的整数舍入改善，不应把每组都宣传为有经济意义的收益。
所有 72 组有两池组合的配置内搜索完成，18 组无可用组合；本轮没有预算耗尽或报价失败。

仍超出 ±0.5% 的两项是：10000 DAI→WETH，约 **−0.5234%**；100000 DAI→WETH，约
**−1.3737%**。它们不是此次 SHIB 多池改进已经解决的案例，需另行检查多跳候选和平台覆盖。
没有为改善均值而隐藏这些负向离群点，也没有在本票中直接扩展未经确认的平台或白名单。

## 同区块重估：剩余差距在哪里

在 SHIB 六行中，5 行支持完整回放。另一行用了当前重估器不支持的 `pancakeswapv3`，
完整输出保持缺失并记录错误，未把部分成功分支合计冒充完整参照。

对支持的行计算两种参照：

1. 按收到的完整分配重新询价，严格检查原始根输入守恒；
2. 去除白名单外交换后，将保留权重重新归一化，再按完整输入重新询价。

第二种明确标记为诊断重分配，不是 ParaSwap 的报告报价，也不是对手重新优化后的最优方案。

| 大额样本 | 多池 vs 原始 ParaSwap | 多池 vs 完整分配同区块重估 | 多池 vs 白名单内重分配 |
|---|---:|---:|---:|
| 33.333… WETH→SHIB | −16.9704 bps | −17.3128 bps | **−2.1167 bps** |
| 80 亿 SHIB→WETH | −13.5498 bps | −13.5533 bps | **−2.8563 bps** |

完整分配中可观察到 BONE（`0x9813037ee2218799597d83d4a5b6f3b6778218d9`）中间路径。
这些结果支持“当前剩余差距与覆盖范围有明显关系”的判断；白名单内仍有约 2–3 bps 的
采样/分配差异，不能把所有差距唯一归因于 BONE，也不能据此证明全市场最优。
诊断调用未将 BONE 或外部池自动加入生产图。

## 延迟与调用成本

| 指标 | 单路径阶段 | 两池完整计算 | 多池完整计算 | ParaSwap HTTP |
|---|---:|---:|---:|---:|
| p50 | 1364 ms | 3523 ms | **4727 ms** | 363 ms |
| p95 | 2012 ms | 5358 ms | **6496 ms** | 575 ms |

当前报价质量更接近，但速度仍明显落后。本地是公共 RPC、debug 构建和逐行新建的固定状态
缓存；这些数字是本轮记录，不是同等基础设施的生产 SLA 对比，也不能将分位数直接相加。

多池计算中的基线阶段共 5101 次 RPC、附加搜索 5502 次 RPC；附加适配器调用为 7603 次。
实验行还运行了两池对照、每行上下文准备和诊断，合计行内 RPC 23135 次；这个总数不是
90 次生产多池请求自身的调用量，不能重复计入候选算法成本。

## 已交付的服务与验证

- `split=true` 接入 `/quote`；`split_max_branches=2` 可比较两池，不能超过服务配置上限。
- 每个真实拆单请求固定区块并返回 `quote_block`；新请求本地缓存不混入其他区块的数据。
- 多分支用 `allocations` 表示，不伪造顺序 `path`；未计算的聚合价格冲击为 `null`。
- `amount_out_min` 检查所选总输出；附加搜索在 HTTP 超时前结束并保留最佳完整方案。
- Viewer 默认勾选多池，可切回单路径，展示比例并高亮全部分支。无 Graph key 的 mock 模式保留离线定价。
- 默认 HTTP 上限调至可配置的 10000 ms，搜索预算 8000 ms；实际完整分配仍可能受用户更短上限限制。
- 77 项离线测试、11 项主网只读测试通过；严格 Clippy、binary 构建、前端生产构建和真实 API 冒烟通过。
